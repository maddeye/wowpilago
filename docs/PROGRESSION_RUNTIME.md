# Native progression runtime

## Integration contract

`src/APProgression.cpp` implements the public `WoWPilago` API in `src/APProgression.h`. Main must compile this source and call `RegisterProgressionScripts()` once from the module loader. This change does not edit the loader, rewards, bridge, schema, or core patch.

`GetState(player)` stores `Cache` in that Player's `CustomData` under `WoWPilago.State`, not in a shared mutable registry. Gameplay hooks run on the player's owning map worker. The joined world phase can apply effects and flush saves after `MapMgr::Update` has joined map workers. This is ownership-based serialization, not a mutex-protected API for arbitrary threads. Callers must not access a Player concurrently or retain state across `RefreshState` or Player destruction. No callback retains a Player pointer. Negative binding lookups live with the Player until explicit refresh or destruction. Binding an online character requires `RefreshState` before AP gameplay.

Startup loads and validates every non-archived binding with a character GUID, but does not populate a global cache or a Player cache. On-demand Player loading also works before `_LoadSpells`, talent calculation, and `_LoadInventory`: the first hooked access uses the assigned character GUID. Each load reads `manifest.catalog_version` with `JSON_UNQUOTE(JSON_EXTRACT(...))` and requires an exact match with compiled `CatalogVersion`. Collection queries include a sentinel row, and binding probes use COUNT, so an empty collection is distinguishable from a query failure. A known binding without its progress row, SQL failure, unsupported/mismatched profile, or bound bot session stops the realm rather than granting unrestricted vanilla progression. The selected failure policy is deliberately fail-stop, not a claim of a graceful per-session rejection API.

Requires protocol-2 tables from `sql/v2.sql`, the pinned core patch's six hooks, one character DB worker, `Rate.Talent=1`, and `MaxPlayerLevel=80`. Startup/config reload checks reject incompatible settings; character talent calculation rejects extra talent points. `Human` rejects missing players/sessions and `WorldSession::IsBot()`. With `MOD_PLAYERBOTS`, it includes `PlayerbotMgr.h` and also rejects players for which `sPlayerbotsMgr.GetPlayerbotAI` returns an AI, including ordinary-session selfbots recognized by that manager. Without that build flag, manager-based detection is unavailable. Bound-profile validation stops on a detected bot; unbound bots retain core behavior. Live playerbots integration remains unverified.

## XP, rewards, talents, and spells

The normalized-XP hook runs after core multipliers. It limits accepted XP to the remaining thresholds through the effective cap. Overflow saturates at half the cap's next-level cost using subtraction before addition, including UINT64_MAX input. At cap 80 it discards overflow without modifying an existing bank. The direct GiveLevel guard and displayed maximum use the same cap.

The transaction-aware `OnPlayerSaveToDB` hook appends absolute `banked_xp`, `last_level`, and `victory` values to the character's own transaction. `last_level` uses the actual Player level; `victory` is 1 exactly at actual level 80, not a copy of the cached flag. Repeating a save does not add bank twice. Full-save rollback therefore keeps character XP/level and progress bank/victory together. There is no independent additive bank routine or additional schema requirement. Unsaved gameplay since the last full save can still be lost in a process crash.

Bank changes in the normalized-XP hook and level changes set the per-Player `savePending` bit. `Reconcile` sets cached victory and pending when it first observes level 80; it does not write victory independently. The joined world update scans online bindings every 5,000 ms of accumulated update diffs. For each bound human with pending work, it constructs a full `Player::SaveToDB` transaction, commits through the single async worker, and waits for the future's boolean. False calls `Stop` before any confirmation or pending reset. Core save construction can already have cleared inventory dirty states, so continuing or retrying that live inventory after failure is unsafe.

After a successful commit, the flush queries and compares character level, progress `last_level`, progress bank, and character XP against live values. Missing/mismatched results stop the realm. Only then does it clear pending and run reconciliation to publish attained level checks. While `savePending` is set, reconciliation does not publish level milestones. This query does not separately read victory or inventory; the successful full transaction, including the save hook, supplies atomic persistence. Ordinary core autosaves and delivery flushes also use the hook but do not clear this pending bit, so a later deferred full save can be redundant. Five seconds is the scan interval, not a hard durability deadline under database load.

Main owns cap receipts and must implement this ordering:

1. Flush live character XP and bank through `SaveToDB` and the single worker before applying a receipt. Wait for the ordered operation and verify its outcome.
2. In the receipt's atomic operation, lock progress and character rows, raise the cap, add the old bank to ordinary character XP, zero the bank, and mark the received index applied. Do not call GiveXP or apply bonuses again. At an ordinarily capped character the bank is at most half one threshold, so release cannot level it up.
3. After verified commit, publish the committed character XP and refreshed cap/bank to the live player, call `RefreshState`, then `Reconcile`. Keep ambiguous outcomes stopped until verified. Do not publish a receipt just because a SQL future became ready.

`RefreshState` preserves a larger live bank when the cap has not changed. Failed or unrelated rewards therefore cannot silently clear unsaved overflow. A changed cap is the explicit handoff to main's atomic bank-release path. Calling refresh before publishing the committed release to the Player is unsupported.

Talent allowance is normal level points minus the reached reservations at 15,20,...,70 plus the smaller of reached reservations and AP unlocks. The result is 59 without unlocks and 71 with all unlocks at 80. Core respec and dual-spec calculations use the same hook. Reconciliation calls `InitTalentForLevel` rather than adding free points directly.

All 72 ability definitions and their generated rank rows are consulted. The root add-spell veto enforces class, unlock, rank level, skill, prior rank, and baseline prerequisites. Saved spell rows have no dependency ordering, so load-time checks defer spell prerequisites until cast/trainer validation. Trainer wrappers are inspected for LEARN_SPELL effects before purchase. The global cast check supplies the second guard. Reconciliation grants eligible base spells only, not every future rank; baseline prerequisite learning, levels, and login retry pending grants.

Riding uses 33388/33391/34090/34091/54197 at 20/40/60/70/77. Journeyman requires Apprentice. Expert supplies Apprentice and Journeyman training without requiring those two useful rewards. Artisan and Cold Weather require Expert. Reconciliation uses core learning, not money deductions. Cast checks reject unowned riding skill grants, mounted use without Apprentice, fast ground use without Journeyman, and flight outside the core/AP flight policy.

## Travel and equipment

The position-aware permission is called by the patched teleport and saved-login roots. Map-only admission permits mixed map 530; the coordinate-bearing calls resolve its zone before arrival. Zones 3430,3433,3487,3524,3525,3557,4080 are Azeroth, including both starter cities and Isle of Quel'Danas. An unresolved destination zone is denied. Other map-530 zones require Outland Access. Ordinary EK/Kalimdor travel stays open and ordinary Azeroth flying stays denied. DK introduction and development maps 609/451/573/606 are denied for bound humans.

The explicit instance/travel classification was checked against the host's build-12340 `data/client-data/dbc/Map.dbc`, 135 rows and 66 fields. It includes Naxxramas 533, TBC Caverns of Time, every expansion dungeon/raid in that DBC, expansion battlegrounds, Northrend transport interiors and the four cross-continent transport maps 610/612/613/614. Map 647, Orgrimmar to Thunder Bluff, is deliberately Azeroth despite its DBC expansion value of 2. Vanilla transport interiors remain Azeroth. Test/development maps are not unlocked by buying continent access. This is source/data inspection, not a live route matrix test.

`IsAuthorized` requires matching character owner GUID, item GUID, entry, and durable binding authorization. The item-level hook changes only the core's minimum-level decision. No equip-error override skips class, proficiency, reputation, unique, holiday, socket, or enchantment checks. Template-only validation remains unchanged.

Trade, same-account mail, and vendor sale hooks reject authorized GUIDs. Reconciliation binds loaded AP items, clears BOP trade windows, and removes refundability. Main must also persist those flags during issuance *before publication*. Core soulbound checks then deny auctions and guild-bank deposits, which have no additional progression callback here. Authorization never follows an item entry to an ordinary copy. Deletion archives the binding within the deletion transaction and retains reward/check history.

## Checks and durable publication

Only catalog IDs enabled for this binding and matching its faction/class/race are inserted. The logical `min_cap` is not an event eligibility condition: a real achievement below a conservative AP logic threshold is still legitimate.

Confirmed quest turn-in uses `OnPlayerCompleteQuest` at the end of RewardQuest plus rewarded-quest status. Zone checks use the actual new zone, matching map, live position access, alive state, and no taxi flight. Login reconciles rewarded quests, all attained level milestones, and current zone. Level changes mark a full save pending. After that save commits and its result is confirmed, reconciliation reports *every* attained milestone, not only the final multiple of five. If logout saves first, login reconciliation recovers the checks from the persisted level. Victory is actual level 80, with no continent/item/raid predicate.

Boss credit uses the per-recipient KillRewarder callback. In this pinned source it executes before `setDeathState`, so checking `victim->IsAlive()` would discard real kills. Credit requires the human's same-map reward distance and the core quest-like alive-or-no-corpse rule. It does not require XP or the human's killing blow, and does not reject a bot-owned killing blow. Normal dungeon difficulty and normal 10/25-player raids are supported; heroic encounters are not curated here.

Dungeon credit persists each configured boss under `(binding,map,instance_id,reset_epoch,boss_id)`, taking the reset epoch from the InstanceSave. All configured IDs must exist for that same instance/reset before a clear is recorded. An absent save or zero epoch is not guessed. Counts include only required boss IDs. The current boss insert is verified, including singleton/last-boss cases. No pre-SetBossState or invented completion callback is used.

Check publication is one `INSERT IGNORE ... SELECT` from the enabled-check/binding rows, followed by a durability query before updating the in-memory completed set. Progression's explicit commits use the ordered single async worker, wait for a true result, and confirm durable rows before publication. Character saves append progress through the save hook; the deferred flush performs the wait and confirmation described above. This blocks the calling gameplay or joined-world thread. A busy realm needs measurements before changing that ordering.

The bridge owns acknowledgement. It must send only persisted unacknowledged rows, retain them across reconnects, and set `acknowledged=1` only after the AP server confirms that location in its checked-location state. This native subsystem never acknowledges its own inserts. Victory uses the durable progress row and the existing binding goal-acknowledgement field remains bridge-owned.

## Verification and release limits

Executed `PYTHONDONTWRITEBYTECODE=1 python3 -m unittest discover -s tests -p test_native_progression.py -v`. All three tests passed with C++17, warnings-as-errors, and undefined-behavior sanitization. The unchanged policy test compiles the production header and generated catalog. It covers huge awards, exact crossings, partial XP, bank saturation, cap80 bank retention, talent reservations/unlocks, riding prerequisites, region/instance classification, and ability base-rank consistency.

Additional tests extract and execute the production bodies of `Commit`, `Reconcile`, `OnPlayerSaveToDB`, and `ProgressionWorld::OnUpdate`. Core Player operations, state lookup, unrelated reconciliation callbacks, and the database/fail-stop boundaries are stubbed. The fixture models atomic transaction success/rollback and core's clearing of inventory dirty state during save construction. It proves false commit stops before confirmation even when persisted level/bank already match, true commit confirms and clears pending, reconciliation makes no independent victory commit, and the 4,999+1 ms flush coordinates victory with character level. It also checks actual-level-derived victory despite stale cache, failed-save rollback in the model, and fail-stop for missing or mismatched level/last-level/bank/XP confirmation. Three milestone regressions also execute the actual level-change callback. They reject publication before the five-second flush, after a failed commit, and after missing or mismatched confirmation. A normal logout before the flush leaves the check recoverable through the next login reconciliation. This is executed production control flow with bounded stubs, not a string-only source check or a real SQL/core integration test. The milestone deferral change is deployed in worldserver `a20ecb1f7917616a3a84eae1cc9bfcb2dec5e0f504fc647204a1e0695b4b5296`. World-only rollout and boot passed bounded preservation review, including separately attributed normal restart system rows. A stock-client test of the exact binary in a new isolated realm now observes the live barrier. At visible level5, a bounded lock on only the new character row blocked the actual save. A SELECT-only observer retained saved4/last_level4/check0 after the input, then saved5/last_level5/check1 after release.989 samples and a second743-sample level10 transition passed; normal relog preserved all checks. These were administrator-assisted level changes, not normal XP-threshold or failed-commit/crash tests. See `verification/native-curated-checks.json` and `verification/curated-check-support.json`.

An earlier validation recorded object compilation with `wowpilago-module-check:latest`, a read-only patched pinned core at `/core`, `-Werror`, no playerbots headers/libraries, and a passing core codestyle check. That compilation was not rerun for this regression verification and is not evidence for the current `MOD_PLAYERBOTS` build.

Not executed here: linked worldserver startup, SQL rollback/fault probes, item issuance/receipt release, live party and reset/restart cases, client equipment/use commands, every travel route, both factions/all classes, or a playthrough/multiworld. Main owns loader integration and realm runs. Object compilation does not verify callback invocation timing beyond the inspected source.

Known release risks remain. The generic mounted-aura restriction needs live quest/temporary-mount and vehicle testing; it currently has no audited exception table. Flying-form and unusual riding skill-grant behavior likewise need real realm evidence. Transport denial recovery is core-patch-owned and cannot be established by this module compilation. Stock-client equip/on-use behavior and the main-owned command fallback are not implemented in these files. The optional `MOD_PLAYERBOTS` detection path needs build and live selfbot evidence. This document does not claim a release-ready full subsystem from unit tests alone.
